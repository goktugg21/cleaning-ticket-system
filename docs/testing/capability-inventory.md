# Capability inventory — every route, page, and capability (P-14 B1)

The checklist the end-to-end audit ticks off (Addendum D §D.24.6; the
P-14 brief §B1): every route, every page, every button/link/form/dialog
on it, who may see it, what it does in one line, and the server call it
makes. **Generated by reading the router and each page component
(2026-09-02, branch `feat/p14-everything-end-to-end`), then confirmed
by clicking in the P-14 walks** — a capability the walks could not
confirm is marked in `p14-findings.md`, not silently kept.

Headline numbers (the report's first number): **~76 surfaces, ~930
discrete capabilities** — operations 545 across 17 sections, admin ~294
across 43 surfaces, customer portal + auth 94 across 16 pages. Counts
are per fragment below; the walks tick them off per role.

Maintenance: update the affected section when a route or page-level
capability is added, moved, or removed (the index rule in
`docs/README.md`).

# Part 1 — Operations surfaces

Fragment covering the route-level surfaces listed below. Derived from `frontend/src/App.tsx` (routes + guards), `frontend/src/auth/permissions.ts` (guard predicates), the page components and their child dialogs, and `frontend/src/api/*.ts` (endpoint resolution; axios base is `/api`). All API paths below are `/api/...`.

Guard predicate facts (from `frontend/src/auth/permissions.ts`):

| Guard | Predicate | Admits |
|---|---|---|
| `ProtectedRoute` (App.tsx) | logged in | every authenticated role |
| `ExtraWorkRoute` | `canAccessExtraWork` | SUPER_ADMIN, COMPANY_ADMIN, BUILDING_MANAGER, CUSTOMER_USER (STAFF excluded — backend `scope_extra_work_for` returns `.none()` for STAFF) |
| `PlannedWorkRoute` | `canAccessPlannedWork` = `isProviderManagementRole` | SUPER_ADMIN, COMPANY_ADMIN, BUILDING_MANAGER |
| `TimesheetsRoute manager` | `canManageTimesheets` | SUPER_ADMIN, COMPANY_ADMIN only (BM deliberately excluded) |
| `ContractsRoute` | `canAccessContracts` | SUPER_ADMIN, COMPANY_ADMIN, BUILDING_MANAGER (BM = server-narrowed reader; writes gated `canManageContracts` = SA/CA) |
| `BillingRoute` | `canAccessBilling` = `isProviderManagementRole` | SUPER_ADMIN, COMPANY_ADMIN, BUILDING_MANAGER |

Role-dispatch helpers on shared routes (App.tsx): `ByCustomer` renders the customer variant for CUSTOMER_USER and the provider page for everyone else — `/extra-work` → MeerwerkTrackerPage (customer) vs ExtraWorkListPage; `/extra-work/new` → MeerwerkFlowPage vs CreateExtraWorkPage; `/extra-work/:id` → MeerwerkDetailPage vs ExtraWorkDetailPage; `/tickets` → redirect to `/my/meldingen` vs DashboardPage variant="tickets-page"; `/tickets/new` → MeldingCreatePage vs CreateTicketPage. The customer (Meerwerk*/Melding*) variants are out of this fragment's scope.

Note on invoices naming: `FacturenPage` at `/invoices` is the PROVIDER invoices overview (BillingRoute). The customer invoices page is `MyInvoicesPage` at `/my/facturen` (CustomerRoute, CUSTOMER_USER only; GET /api/invoices/my/ etc.) — out of scope.

Extra-work tab routes: `/extra-work/to-price`, `/extra-work/with-customer`, `/extra-work/approved`, `/extra-work/finished` are static sibling routes of `/extra-work`, all rendering ExtraWorkListPage with the tab preselected (`EXTRA_WORK_TABS` in `frontend/src/lib/extraWorkTabs.ts`). `/extra-work/request-quote` redirects to `/extra-work/new`; `/tickets/chargeable` redirects to `/extra-work/approved`.

# Part 3 — Customer portal and auth

Scope: the customer portal (role `CUSTOMER_USER`) and the three auth pages.
Sources: `frontend/src/App.tsx` (routes/guards), `frontend/src/layout/AppShell.tsx`

(the axios client adds it).

Guard glossary:
- **ProtectedRoute** — any authenticated user (redirect `/login` when anonymous). Scoping stays backend-side.
- **CustomerRoute** — `isCustomerUser(me.role)` (ONLY `CUSTOMER_USER`); others bounce to `/`.

- Customer-side ACTION permissions (`customer.*` keys, frozenset `CUSTOMER_PERMISSION_KEYS` in `frontend/src/api/types.ts`) are resolved **server-side**; the UI reads the result via `me.can_manage_documents`, per-record `actions.can_*`, and `allowed_next_statuses` — it never evaluates the keys itself.
